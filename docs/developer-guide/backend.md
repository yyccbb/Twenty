# Backend developer guide

Repo: [`Twenty-backend`](../../../Twenty-backend/README.md). The rules it enforces: [rules.md](rules.md). The repo's `AGENTS.md` is a compact summary of the rules, written for coding agents and equally useful for people.

---

## 1. What the backend owns

The iOS app owns the UI, local notifications (planning prompts, start/finish prompts, cues) and an on-device cache. The backend owns everything that must be **trusted, shared across devices, or secret**:

| Responsibility | Why it lives on the server |
|---|---|
| Accounts and sign-in | One identity across iOS and the future web app |
| Calendar (planned events and cues) | Synced across devices; the web app reads the same data |
| Start/finish records and the [rules](rules.md) | Final recorded times must not be editable by the client |
| Token ledger and badges | Currency must be tamper-proof; the balance is derived from a ledger |
| Goals and AI breakdown | AI API keys stay secret; prompts and cost limits are controlled centrally |
| User settings (time zone, planning-prompt schedule) | Synced so a new device or the web app picks them up; each device still schedules its own notifications |

What the backend does **not** do in the MVP: send push notifications, real-time sync, or anything social.

## 2. Stack

| Layer | Choice | Why |
|---|---|---|
| Language / runtime | **TypeScript on Node.js 22 LTS** | Same language as the future web app, so the web app and server share one copy of the rules code and the API types. Largest ecosystem for AI SDKs. Easy to run in Docker on Alibaba Cloud. |
| HTTP framework | **Hono** with `@hono/zod-openapi` | Small and fast. Each route's request/response schema is written once in Zod and **the OpenAPI document is generated from it**. |
| API contract | **OpenAPI 3.1** (generated) → `contracts/openapi.yaml` | iOS client generated by Apple's `swift-openapi-generator`; web client by `openapi-typescript`. |
| Validation | **Zod** | Same schemas validate requests, AI output and config |
| Database | **PostgreSQL 17** | Strong transactions for the token ledger, `timestamptz`, JSONB for AI output |
| ORM / migrations | **Drizzle ORM + drizzle-kit** | SQL-like, typed, migrations are plain SQL files you can read |
| Background jobs and cron | **pg-boss** (job queue stored in Postgres) | Runs AI breakdowns in the background and nightly maintenance with no Redis to operate |
| Auth | **Sign in with Apple** (server verifies Apple's ID token with `jose`) or **email + password** (scrypt hash; email format checked, not verified, in the MVP) → issues own **JWT access token (15 min) + rotating refresh token** | Works in China; email also covers users without an Apple ID and the web app; phone/SMS can be added for the China launch |
| AI | **DeepSeek Flash** (`deepseek-flash`) through DeepSeek's OpenAI-compatible API (the `openai` SDK with a custom `baseURL`), behind an `AiProvider` interface | Claude and OpenAI don't serve mainland China or Hong Kong. Behind the interface, a global deployment can switch to Claude without code changes elsewhere. |
| Logging | **pino** (JSON logs) → `docker logs` for the MVP | Cheap; can ship to Alibaba Cloud's log service (SLS) later |
| Testing | **Vitest** + **Testcontainers** (real Postgres) | Rules engine tested against the shared test cases; ledger tested against a real database |
| Packaging | Docker image, deployed with Docker Compose (Caddy + api + worker + postgres) | Same image runs in HK now and in a mainland region later |

> **Not switched yet:** the code still calls Qwen through Alibaba Cloud Model Studio (`src/ai/qwen.ts`, `AI_PROVIDER=qwen` and the `QWEN_*` variables in §11). Moving to DeepSeek Flash means adding a DeepSeek provider in `src/ai/` and its variables in `src/config.ts`; nothing else depends on the provider.

## 4. Local setup

```sh
npm ci
cp .env.example .env     # set JWT_SECRET (≥ 32 chars) and APPLE_CLIENT_IDS
                         # AI_PROVIDER=fake runs without a Qwen key or network
docker run -d --name twenty-pg -p 5432:5432 \
  -e POSTGRES_USER=twenty -e POSTGRES_PASSWORD=twenty postgres:17-alpine
npm run migrate:dev      # applies src/db/migrations
npm run dev              # API on :3000 (OpenAPI at /openapi.json, health at /healthz)
npm run dev:worker       # jobs and cron, in a second terminal
```

The API and worker are separate processes from the same code. Without the worker, start/finish still work, but auto-finish, missed-event sweeps and AI breakdowns never run.

## 5. Architecture tour

```
src/rules/     pure rules: grid, snap, start, finish, extend + cascade, overlap, tokens, time zones
src/services/  business operations; own transactions and locking
src/routes/    Hono routes + Zod schemas (the OpenAPI source)
src/auth/      Apple ID token verification, email + password (scrypt), JWT access tokens, refresh rotation
src/ai/        AiProvider interface, qwen.ts, fake.ts, prompt + output validation
src/jobs/      pg-boss queue names, options and handlers
src/db/        Drizzle schema, plain-SQL migrations, UUIDv7
src/lib/       errors, logger, clock, pagination
server.ts / worker.ts / migrate.ts   entry points (dist/*.js in the image)
```

What goes where:

- **`src/rules` is pure.** Inputs in, outputs out: no `Date.now()`, no DB, no env. If you need "now", the service passes it in from `deps.clock`. This is what makes the rules testable against the shared fixtures and portable to Swift.
- **Services own correctness.** A service opens the transaction (`transaction()` in `src/db/client.ts`), calls `lockUser` (`SELECT … FOR UPDATE` on the user row) before touching the calendar or ledger, loads state, calls the rules, and writes. Per-user writes are therefore serialised.
- **Routes stay thin.** Validate with Zod, call one service, shape the response. The Zod schemas *are* the API contract.
- **Jobs are enqueued inside the transaction.** `transaction()` exposes an `executeSql` that pg-boss uses, so an `events.auto_finish` job exists exactly when the start that needs it committed. Never enqueue after commit.
- **Only `src/ai` knows the provider.** Everything else uses `AiProvider`. Claude and OpenAI aren't available in mainland China or Hong Kong; keeping this boundary lets a global deployment switch providers by config.

## 6. Data model

A summary of `src/db/schema.ts`, which is the source of truth. `?` marks a nullable column. Every timestamp is a `timestamptz`, and every `id` is a UUIDv7.

```
users             id, apple_sub? (UNIQUE), email? (lower-cased, trimmed, UNIQUE), password_hash?,
                  display_name?, timezone (default UTC), token_balance, created_at, deleted_at?
refresh_tokens    id, user_id, token_hash (UNIQUE), device_label?, created_at, expires_at,
                  revoked_at?, replaced_by_id?                                 ← rotation chain
user_settings     user_id (PK), planning_prompts (JSONB: [{weekday[], local_time}]),
                  day_end_local_time (default 00:00), preferences (JSONB), updated_at

goals             id, user_id, title, description?, target_date?, status(active|achieved|archived),
                  created_at, updated_at
ai_breakdowns     id, goal_id, user_id, status(queued|running|done|failed), model?, prompt_version,
                  request (JSONB: hints, max_items), result? (JSONB: summary, items[]), error?,
                  tokens_used?, created_at, updated_at
events            id, user_id, title, notes?, goal_id?, breakdown_item_id?,
                  kind(cadenza|tutti, default cadenza),
                  planned_start (on grid), duration_bars (≥ 1),
                  status(planned|in_progress|done|missed|cancelled),           ← Tuttis: planned or cancelled
                  version (optimistic locking), created_at, updated_at
event_records     event_id (PK), start_tapped_at?, finish_tapped_at?,          ← Cadenzas only; raw device times
                  recorded_start?, recorded_end?, late_bars, early_bars,       ← computed by the server
                  extended_bars, finish_kind?(on_time|shortened|auto|abandoned), tokens_awarded?,
                  original_planned_start, original_planned_end, rules_version  ← plan before early start / extend / shift
event_changes     id, event_id, kind(extend|cascade_shift|early_start), delta_bars,
                  caused_by_event_id?, created_at                              ← audit trail for shifts
cues              id, user_id, series_id, title, notes?, dtstart, timezone, rrule? (RFC 5545),
                  until? (exclusive; set when a series is split), version, created_at, updated_at
cue_occurrences   cue_id, original_at, status(done|skipped|snoozed|moved|cancelled), new_at?,
                  detached_cue_id?, updated_at  (PK: cue_id + original_at)

reward_rules      version (PK), tokens_per_bar (even, > 0), early_bar_rate, extended_bar_rate,
                  auto_finish_deduction_bars, created_at
token_ledger      id, user_id, delta (±), reason(event_reward|badge_redeem|adjustment), ref_id?,
                  rules_version?, idempotency_key (UNIQUE), created_at
badges            id, code (UNIQUE), name, description?, cost (≥ 0), image_url?, active, created_at
user_badges       user_id, badge_id, ledger_entry_id, acquired_at  (PK: user_id + badge_id)
idempotency_keys  user_id, key, method, path, request_hash, status_code?, response_body?,
                  created_at  (PK: user_id + key)                              ← HTTP replays, purged after 24 h
```

- The **ledger is append-only**: a trigger rejects UPDATE, DELETE and TRUNCATE, so corrections are new `adjustment` entries. `idempotency_key` makes retries from flaky networks safe (no double rewards). `users.token_balance` is a cached sum of the ledger, updated in the same transaction as each insert.
- The database enforces the grid itself: `planned_start` must be a multiple of 20 minutes, and `duration_bars` ≥ 1.
- In `cue_occurrences`, `cancelled` means that one occurrence was deleted. Editing one occurrence's content creates a standalone cue, linked by `detached_cue_id`.
- **Account deletion** keeps a stripped `users` row (no Apple ID, email, password or name), because the ledger references it.
- **Behind the rules:** `cancelled` in `events.status` predates the rule that deleting an event removes it ([rules](rules.md)). Until the backend catches up, the schema keeps it, and `DELETE /v1/events/{id}` still cancels instead of deleting.

## 7. API

REST + JSON over HTTPS, versioned under `/v1`, described by the generated OpenAPI document (`contracts/openapi.yaml`, also served at `/openapi.json`). Every write that changes state accepts an `Idempotency-Key` header. Errors use one shape: `{ "error": { "code": "bar_misaligned", "message": "..." } }`. The [frontend guide](frontend/README.md) covers the client's side: auth, error codes, idempotency and versions.

| Group | Method & path | Purpose |
|---|---|---|
| **Auth** | `POST /v1/auth/apple` | Exchange Apple ID token → access + refresh tokens (creates the user on first sign-in) |
| | `POST /v1/auth/email/signup` | Email + password → access + refresh tokens. `409 email_taken` if the address is in use |
| | `POST /v1/auth/email/signin` | Email + password → access + refresh tokens. `401 invalid_credentials` for a wrong password or unknown email alike |
| | `POST /v1/auth/refresh` | Rotate refresh token |
| | `POST /v1/auth/logout` | Revoke current refresh token |
| **Account** | `GET /v1/me` | Profile, `timezone`, `timezone_supported`, token balance and `settings` (`planning_prompts`, `day_end_local_time`, `preferences`) |
| | `PATCH /v1/me/settings` | Time zone, planning-prompt schedule, day end, preferences |
| | `DELETE /v1/me` | Account deletion (**required by App Store rules** for apps with sign-in) |
| **Calendar** | `GET /v1/events?from=&to=` | Events in a date range (cursor-paginated) |
| | `GET /v1/events/{id}` | One event with its start/finish record |
| | `POST /v1/events` | Create a Cadenza or Tutti (`kind`); rejects off-grid start, non-integer bars, or a Cadenza overlapping another (`409 cadenza_overlap`) |
| | `PATCH /v1/events/{id}` | Reschedule / edit / switch `kind` (uses `version` for conflict detection) |
| | `DELETE /v1/events/{id}` | Delete. The event and its change history are removed; there is no cancelled state. Only planned events can be deleted; a Cadenza that has started, finished or been missed gets `409 invalid_state`, since its record, and any tokens it earned, must stay |
| | `GET /v1/calendar?from=&to=` | Events + **expanded** cue occurrences in one call (also what iOS uses to schedule notifications) |
| **Recording** (Cadenzas only; a Tutti gets `409 not_cadenza`) | `POST /v1/events/{id}/start` | Body `{tapped_at}` → `recorded_start`, early/late bars; `409 cadenza_overlap` if an early start would overlap another Cadenza; `409 cadenza_in_progress` if another Cadenza hasn't finished yet |
| | `POST /v1/events/{id}/extend` | Body `{bars, dry_run?}` (in progress only) → new end; returns **every Cadenza pushed by the cascade** and day-end warnings. `dry_run: true` returns the preview without saving |
| | `POST /v1/events/{id}/finish` | Body `{tapped_at}` → `recorded_end`, finish kind (on time / shortened / abandoned), **tokens awarded**. Auto-finish comes only from the job; a tap made by `E + 5` that arrives after it replaces it once ([rules §4](rules.md#4-finishing-a-cadenza)). A tap after `E + 5` gets `409 window_closed` |
| **Cues** | `GET/POST/PATCH/DELETE /v1/cues[/{id}]` | CRUD for cues, including repeat rules. `PATCH` and `DELETE` on a repeating cue take `{scope: this \| following \| all, occurrence}` |
| | `PUT /v1/cues/{id}/occurrences/{original_at}` | Mark one occurrence done / skipped / snoozed / moved |
| **Goals & AI** | `GET/POST/PATCH/DELETE /v1/goals[/{id}]` | Long-term goals CRUD |
| | `POST /v1/goals/{id}/breakdowns` | Start AI breakdown → `202 {breakdown_id}` (background job) |
| | `GET /v1/breakdowns/{id}` | Poll status + suggested activities (each sized in 20-min bars) |
| | `POST /v1/breakdowns/{id}/accept` | Body: chosen items + times → creates events in one transaction |
| **Tokens & badges** | `GET /v1/tokens/ledger?cursor=` | Paged token history, newest first |
| | `GET /v1/badges` | Badge catalog + which ones the user owns |
| | `POST /v1/badges/{id}/redeem` | Spend tokens (fails if balance is too low; done in one transaction) |
| **Ops** | `GET /healthz` | Liveness for monitoring |
| | `GET /openapi.json` | The OpenAPI document |

Deliberately absent for the MVP: a general sync endpoint, WebSockets, and an admin API (use SQL directly, §12).

## 8. Common workflows

### Add or change an endpoint
1. Define or extend Zod schemas in `src/routes/schemas.ts` (shared) or the route file.
2. Register the route with `createRoute` in the matching `src/routes/*.ts`. Reuse `IdempotencyHeaders`, `PageQuery`, `errors`, `security` from `src/routes/common.ts`.
3. Put the logic in a service; throw `AppError(status, 'snake_case_code', message)` for expected failures.
4. `npm run openapi` to regenerate `contracts/openapi.yaml`, then commit it **with** the route change. `test/openapi.test.ts` fails if they drift.
5. Update the endpoint table in §7.
6. Tell the client developers: they regenerate their clients from the new yaml.

### Change the database schema
1. Edit `src/db/schema.ts`.
2. `npm run db:generate` writes a new SQL file to `src/db/migrations/`. Read it; hand-edit only to add what Drizzle can't express (triggers, seeds), as `0001_ledger_append_only_and_seed.sql` does.
3. `npm run migrate:dev`, run the tests, commit schema + migration + snapshot together.
4. Migrations only go forward. Never edit one that has been deployed.

### Change a rule
1. Rules are product decisions: confirm against [rules.md](rules.md), or ask. Don't invent timing or token behaviour.
2. The fixtures change first (in `../Twenty`, by whoever owns the rules). Then update `src/rules`, run `npm run test:rules`, and let the iOS developers know the Swift port must follow.

### Change reward values
Insert a new `reward_rules` row with the next version. Never update an existing row: ledger entries record the version they were paid under.

### Add a background job
1. Add the name to `JOBS` in `src/jobs/queue.ts` (with retry options if it needs them); `ensureQueues` creates it on boot for both the API and the worker.
2. Add the handler in `src/jobs/handlers.ts` and register it in `src/worker.ts` (plus a `schedule` call for cron jobs).
3. Enqueue through the `Queue` interface, passing the transaction when the job must exist only if the write commits.

## 9. Invariants you must not break

| Invariant | How it's enforced |
|---|---|
| Token ledger is append-only; corrections are new entries | DB trigger rejects UPDATE/DELETE/TRUNCATE on `token_ledger` |
| `users.token_balance` equals the ledger sum | `appendLedgerEntry` (`src/services/ledger.ts`) updates both in one transaction |
| A Cadenza pays out once | Ledger `idempotency_key` is UNIQUE; rewards use `event_reward:<event_id>` |
| Retried writes don't repeat | `Idempotency-Key` middleware stores the first response (below 500) for 24 h and replays it |
| Concurrent edits don't clobber | Events and cues carry `version`; stale writes get `409 version_conflict` |
| Recorded times are the server's | Clients send raw `tapped_at`; `src/rules` computes the rest |
| Grid math in UTC | Only whole-hour time zones are supported (`isSupportedTimezone`) |
| Primary keys are UUIDv7 | `uuidv7()` in `src/db/ids.ts` |
| Every log line has a request ID | `requestContext` middleware + pino mixin (`src/lib/logger.ts`) |

## 10. Testing

```sh
npm test            # everything; Docker must be running (Testcontainers starts postgres:17-alpine)
npm run test:rules  # rules engine against fixtures.json (RULES_FIXTURES_PATH overrides the location)
npm run typecheck
```

- **Rules:** every fixture group (`snap`, `start`, `finish`, `tokens`, `extend`, `create`, `timezone`) must match exactly, with no extra keys; times compare as instants.
- **Integration:** `test/integration/harness.ts` boots a real Postgres, runs migrations and gives you an app with a `FixedClock` you can advance. Never mock the database for ledger, recording or transaction tests.
- **Contract:** `test/openapi.test.ts` fails if `contracts/openapi.yaml` is stale.
- Changes to rules, ledger or recording need tests. Report failing tests honestly; don't loosen assertions to pass.

## 12. Deploy and operations

The MVP is a test in China with one user: one server on Alibaba Cloud Hong Kong running `docker-compose.yml`:

| Service | Runs | Notes |
|---|---|---|
| `postgres` | Postgres 17 | Data in the `pgdata` volume |
| `migrate` | `node dist/migrate.js` once | api and worker wait for it to succeed |
| `api` | `node dist/server.js` | Stateless; port 3000 behind Caddy |
| `worker` | `node dist/worker.js` | pg-boss jobs and cron |
| `caddy` | reverse proxy | Automatic HTTPS for `DOMAIN` (`deploy/Caddyfile`) |

- **Image:** one `Dockerfile` for api, worker and migrate. In mainland China, build with `--build-arg NODE_IMAGE=<ACR mirror> --build-arg NPM_REGISTRY=https://registry.npmmirror.com`, and point `TWENTY_IMAGE`, `POSTGRES_IMAGE`, `CADDY_IMAGE` at Alibaba Container Registry copies. Docker Hub is unreliable from the mainland.
- **Health:** `GET /healthz` returns `{"status":"ok"}`.
- **Logs:** `docker compose logs -f api worker`. JSON lines; follow one request with its `request_id` (also returned as `X-Request-Id`).
- **Jobs:** `events.auto_finish` (delayed to E+5), `events.close_stale` (every 20 min), `ai.breakdown`, `db.backup` (nightly `pg_dump` to OSS), plus an hourly purge of stored idempotency keys.
- **Admin:** there's no admin API; use SQL (`docker compose exec postgres psql -U twenty`). Never UPDATE or DELETE ledger rows; insert an `adjustment` entry instead.

## 13. CI/CD

The repo has no CI configured yet. This is the recommended pipeline; the steps apply to any CI system.

**On every pull request** (all must pass before merge):
1. Check out `Twenty-backend` and `../Twenty` side by side (or set `RULES_FIXTURES_PATH`), so the rules tests find the fixtures.
2. `npm ci`
3. `npm run typecheck`
4. `npm test`. The runner needs Docker for Testcontainers. This includes the rules fixtures and the OpenAPI drift test.
5. Migrations in sync: `npm run db:generate` must produce no new file (`git status --porcelain src/db/migrations` is empty).
6. `npm run build`

**On merge to `main`:**
1. Build the image once and tag it with the git SHA (optionally also `latest`).
2. Push it to Alibaba Container Registry (Hong Kong), not Docker Hub.

**Deploy** (manual approval at first, while there is one server):
```sh
# on the server, in the compose directory
export TWENTY_IMAGE=registry.cn-hongkong.aliyuncs.com/<namespace>/twenty-backend:<sha>
docker compose pull
docker compose up -d         # migrate runs first; api and worker start after it succeeds
curl -fsS https://$DOMAIN/healthz
```
Roll back by deploying the previous SHA tag. Migrations only go forward, so a schema change must stay compatible with the previous image until the rollback window has passed. Split risky changes: add a column first, start using it in a later release.

Example GitHub Actions workflow (adapt the registry, secrets and fixtures checkout to your setup):

```yaml
# .github/workflows/ci.yml
name: ci
on:
  pull_request:
  push:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest          # has Docker, which Testcontainers needs
    steps:
      - uses: actions/checkout@v4
        with: { path: Twenty-backend }
      - uses: actions/checkout@v4   # the shared fixtures
        with: { repository: <owner>/Twenty, path: Twenty, token: ${{ secrets.FIXTURES_TOKEN }} }
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm, cache-dependency-path: Twenty-backend/package-lock.json }
      - run: npm ci
        working-directory: Twenty-backend
      - run: npm run typecheck && npm test && npm run build
        working-directory: Twenty-backend
      - name: Migrations match schema
        working-directory: Twenty-backend
        run: npm run db:generate && test -z "$(git status --porcelain src/db/migrations)"
  image:
    needs: test
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: registry.cn-hongkong.aliyuncs.com
          username: ${{ secrets.ACR_USERNAME }}
          password: ${{ secrets.ACR_PASSWORD }}
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: registry.cn-hongkong.aliyuncs.com/<namespace>/twenty-backend:${{ github.sha }}
```

`../Twenty` is not a git repository yet. Until it is, CI can't check it out: either make it a repo, or vendor a copy of `fixtures.json` into CI and point `RULES_FIXTURES_PATH` at it.

## 14. Decisions the backend made

Where the product rules were silent, the backend made eleven calls of its own: late offline taps, the close_stale backstop, account deletion, unsupported time zones, the day-end anchor, cue details, size caps, abandoned events, the AI limit's day, refresh-token reuse, and the default event kind. They are listed in the [backend README](../../../Twenty-backend/README.md#decisions-the-rules-left-open). If you change one, update that list.

## 15. Troubleshooting

| Symptom | Fix |
|---|---|
| `createZstdDecompress.bind` / undici error at startup or in tests | Node < 22.19 with an unpinned `openai` or `testcontainers`. Keep them at `openai@6` and `testcontainers@11`, or upgrade Node. |
| Integration tests hang or fail to start Postgres | Docker isn't running. |
| `contracts/rules/fixtures.json not found` | Put `../Twenty` next to the repo, or set `RULES_FIXTURES_PATH`. |
| 401s in a test after advancing the clock | Access tokens last 15 minutes of *fake* time. Use the harness's per-request tokens. |
| `tsx: command not found` | `node_modules` is missing (for example after removing a git worktree). Run `npm ci`. |
| `Invalid configuration: …` at boot | A required env var is missing or invalid; the message names it. |
| `422 unsupported_timezone` | The user's zone isn't a whole number of hours from UTC (India, Nepal, …). That's intentional: grid math runs in UTC, which is only correct for whole-hour zones ([rules §1](rules.md#1-the-20-minute-grid-and-time-zones)). |
